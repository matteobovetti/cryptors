# AES performance plan

Scope: `src/aes/` (the three key sizes, both directions and the key schedule) and the `BlockCipher` trait in
`src/block_cipher.rs`, which step P1 extends. Targets are aarch64 and x86-64. The Go reference is go1.27.1:
`src/crypto/aes/aes.go`, a thin wrapper around `src/crypto/internal/fips140/aes/`. The files used here are:

- `aes.go`, plus `aes_asm.go`/`aes_noasm.go` for dispatch.
- `aes_generic.go` and `const.go`, the portable code.
- `aes_arm64.s`, and `aes_amd64.s`, which is generated from `_asm/standard/aes_amd64.go`.
- The CTR code, which is where Go's speed is: `ctr.go`, `ctr_asm.go`, `ctr_arm64.s` (generated by
  `ctr_arm64_gen.go`) and `ctr_amd64.s` (generated from `_asm/ctr/ctr_amd64_asm.go`).

These were read from the local toolchain (`/usr/local/go`, `go1.27.1`), which is the same tag as
`cs.opensource.google/go/go/+/refs/tags/go1.27.1`.

Everything below was measured on 2026-10-09 on the Apple M1 Pro, unless a line says otherwise. The clock was 3.16 GHz
by an `add` chain, the load average 3.8–5 (desktop), on AC power, with no thermal warning. Prototypes were
throwaway copies of the tree under `/tmp`. The repository was not touched, and the code that matters is
reproduced here. x86 timings can only come from the GitHub runners (§4). The x86 figures here are llvm-mca
estimates, and the x86 correctness runs used Docker and Rosetta.

Today the other crate's loop does a `bl <Aes128 as BlockCipher>::encrypt_block` per block. The out-of-line
function reloads all 11 round keys and returns the block through memory. `encrypt_block` is neither generic nor
`#[inline]`, so without LTO it cannot be inlined across crates. The README's sentence "the aarch64 backend is
compiled into the caller's loop" is true only of the crate's own test.

The runtime-dispatch rows are what every x86-64 build and every `aarch64-unknown-linux-gnu` build gets. `aes` is not
in those targets' baseline, so `has_hw_aes()` is a runtime check. Also, a `#[target_feature(enable = "aes")]` function
cannot be inlined into a caller without the feature. So whatever the wrapper does, each block is a call into
`aarch64::encrypt` or `x86::encrypt`. The disassembly confirms this for `aarch64-unknown-linux-gnu`: it loads the
`std_detect` cache, tests bit 3 and calls the backend. Building with `-C target-feature=-aes` on the Mac reproduces
that path natively. Only moving the loop inside the backend fixes it (P1 + A1/X1).

### M1 AES instruction timings (cycles; dependent `asm!` chains, calibrated against an `add` chain)

| Sequence | Cycles |
|----------|--------|
| `AESE` + `AESMC` on the same register (fused), dependent | 3.0 |
| `AESE` then `AESMC` into another register (not fused), dependent | 5.0 |
| `AESD` + `AESIMC` fused, dependent | 3.0 |
| fused pairs, 4 independent chains | 0.75 per pair |
| fused pairs, 8 independent chains | 0.39 per pair |
| fused pairs, 12 or 16 independent chains | **0.26–0.27 per pair** (4 per cycle) |
| `AESIMC` alone, independent | 0.25 |
| GPR → `DUP` → `AESE` → `UMOV` → GPR (the key schedule's `sub_word`) | **15.1** |

The AES-128 floor is therefore 10 × 0.25 = 2.5 cycles per block, about 19.3 GiB/s at 3.16 GHz. It needs 12 blocks in
flight (3-cycle latency × 4 per cycle). The test's loop reaches 3.95 because the out-of-order core finds that overlap
by itself. The 8-block prototype reaches 3.3 and the 12-block one 3.1. At about 22 instructions per block, the
frontend bound is near 2.75 (an estimate that assumes 8-wide decode).

## 2. What Go does, and what we take from it

- **Single block** (`encryptBlockAsm`, `decryptBlockAsm`). On arm64 these are `AESE`/`AESMC` pairs on one register,
  with keys loaded four at a time by `VLD1.P`. On amd64 it is a `MOVUPS` and an `AESENC` per round. Our backends
  compile to the same sequences: LLVM writes `AESE` into the key register, but the pairs stay fusible. So there is
  nothing to take. Go's 22.8 cycles per block (§1) is not AES: it is the `cipher.Block` interface call, the length and
  overlap checks, and `fips140.RecordNonApproved` on every block.
- **Several blocks** (`ctrBlocks{1,2,4,8}Asm`). This is where Go is fast. Go interleaves **8 blocks round by round**.
  On arm64 the blocks sit in V0–V7 and all 15 round keys in V8–V22. On amd64, which has 16 XMM registers, each round
  key is loaded once and fed to 8 `AESENC`s. `XORKeyStreamAt` runs 8-block groups, then a 4, 2, 1 tail. **We take the
  interleave and the tail shape (P1, A1, X1).** Go uses this only inside CTR and GCM. Its `cipher.Block` stays one
  block per call, so nothing in Go's public API is a multi-block ECB call, and `TestThroughputBulk` (CTR) stays the
  reference point.
- **Key expansion.** The arm64 `expandKeyAsm` runs one round per loop iteration. It moves the last word into a vector
  (`VMOV`), and a `VTBL` with `rotInvSRows` rotates it and undoes ShiftRows in advance, so the S-box result lands in
  lane 0. Then come an `AESE` with a zero key, a `VMOV` back, and four `EORW`s. The amd64 code uses `AESKEYGENASSIST`
  and the `SHUFPS`/`PXOR` prefix from Intel's white paper, a whole round key per register. Both build the
  decryption keys with `AESIMC` in reverse order, as ours does. **We take the one-round-per-iteration structure
  (K1).** The lack of it is the whole reason Go's key setup is twice as fast as ours. For K2 we go a step further
  than Go's arm64 code, to OpenSSL's `aesv8-armx.pl`, which never leaves the vector registers.
- **Generic code** (`aes_generic.go`, `const.go`). Four T-tables per direction plus S-box tables for the last round:
  the design of our scalar, which is 1.37x faster. Nothing to take.
- Go has **no VAES, VPCLMULQDQ or AVX-512** code anywhere under `crypto/` in 1.27.1 (by grep), so X2 has no Go
  counterpart. Go requires SSSE3 and SSE4.1 next to AES-NI (`supportsAES`); see K2.

### D1. `#[inline]` on the three methods of the AES types

This adds `#[inline]` on `new`, `encrypt_block` and `decrypt_block` in the `aes!` macro. It changes where the code is
compiled, not what is compiled. Measured from another crate: AES-128 7339 → 11734 MiB/s (+60%), AES-192 6412 → 9651,
AES-256 5337 → 8206. That equals fat LTO (11939).

It pays wherever the backend can be inlined into the caller: aarch64-apple-darwin, and any build with
`-C target-feature=+aes` or `-C target-cpu=native`. Under runtime dispatch it removes the wrapper's frame (on x86, the
six pushes and pops per block: llvm-mca 37 → 21 cycles on skylake). The call into the backend stays, though (7122
MiB/s on the M1), and removing it is P1's job. Even with D1, the per-block figure is fragile: in a larger generic
harness, the same binary measured about 8200 MiB/s, because LLVM decided not to inline.

- Gate: B1's crate at least 1.4x faster on the Mac, and the crate's own `throughput` unchanged (±3%).
- Docs: the README's Benchmarking paragraph. Its "compiled into the caller's loop" sentence must say that it holds in
  other crates only where `aes` is in the target's baseline, and it gains the other-crate row.

### K1. Key expansion one group at a time

The disassembly of `aarch64::expand_key::<16, 11>` shows where the time goes. `schedule::key_expansion` loops over
words and picks `SubWord` with `if i % nk == 0`. LLVM if-converts that into a `csel`. So the `DUP` → `AESE` → `FMOV`
round trip (15 cycles, §1) runs for all 40 words, and every word waits for it: about 40 × 17 ≈ 680 of the ~810
cycles. The x86 backend and the scalar backend use the same generic loop.

Rewrite the loop to handle `Nk` words per iteration. `SubWord` then runs once per group by construction, as in Go's
`ks128Loop`. The prototype keeps the `w` array and its wipe:

```rust
let mut rcon = 1u8;
let mut i = nk;
while i < 4 * N {
    w[i] = w[i - nk] ^ sub_word(w[i - 1].rotate_right(8)) ^ u32::from(rcon);
    rcon = (rcon << 1) ^ (0x1b * (rcon >> 7));
    for j in 1..nk {
        if i + j == 4 * N {
            break; // the last group of AES-192 and AES-256 is partial
        }
        let temp = if nk > 6 && j == 4 { sub_word(w[i + j - 1]) } else { w[i + j - 1] };
        w[i + j] = w[i + j - nk] ^ temp;
    }
    i += nk;
}
```

Measured `new` plus drop, FEAT_AES: 258 → 78 ns (AES-128), 294 → 74 (AES-192), 349 → 100 (AES-256). That puts all three
below Go's 122/113/138. Scalar: 168 → 150 ns (AES-128) and 211 → 191 (AES-256). The eight AES unit tests pass on the
prototype, including `matches_scalar_backend`, which compares the round keys of both directions for 256 keys per
size, and `many_keys`, which uses 1000 keys per size.

- Gate: FEAT_AES key setup at least 2x faster; `throughput` unchanged, since it does not run this code.
- Docs: the `key_expansion` comment says that `SubWord` runs once per group. Do not cite cycle counts in `*.rs`.

### K2. Key expansion in vector registers

After K1, the AES-128 schedule is 10 dependent rounds of about 19 cycles each, nearly all of it the round trip between
GPRs and vectors. OpenSSL's `aesv8-armx.pl` never leaves the vector unit. Its `.Loop128` (checked against current master) is
`vtbl` with the "rotate-n-splat" mask `0x0c0f0e0d`, then `vext` from a zero register, `aese` with a zero key, and
`veor`s. The prototype in intrinsics:

```rust
let rot_splat = vreinterpretq_u8_u32(vdupq_n_u32(0x0c0f0e0d)); // RotWord(w3) in every column
let mut rcon = vdupq_n_u32(1);
for i in 1..N {
    let t = veorq_u8(vaeseq_u8(vqtbl1q_u8(k, rot_splat), zero), vreinterpretq_u8_u32(rcon));
    let mut x = veorq_u8(k, vextq_u8::<12>(zero, k)); // w0, w0^w1, w1^w2, w2^w3
    x = veorq_u8(x, vextq_u8::<8>(zero, x));          // w0, w0^w1, w0^w1^w2, w0^..^w3
    k = veorq_u8(x, t);
    enc[i] = store(k);
    let r = vgetq_lane_u32::<0>(rcon);
    rcon = vdupq_n_u32(((r << 1) & 0xff) ^ (0x1b * (r >> 7)));
}
```

Measured: AES-128 `new` plus drop 78 → **30 ns**, 8.6x faster than today and 4x faster than Go. All AES tests pass.
My first version had an `Rcon` overflow at `0x80`. It was caught at once by `known_answers`, `chained`, `many_keys`
and `matches_scalar_backend`, so the existing suite is a sufficient check for this step.

- **AES-256**: the same, plus the half-step that splats `w7` without rotating it and applies `AESE` without `Rcon`.
  **AES-192**: its 6-word stride straddles vectors, and OpenSSL handles it with 64-bit halves. Leave it on K1, which
  is already 74 ns and below Go's 113, unless it comes out cheaply.
- **x86**: the same shape, with two candidates for the S-box step. One is a `PSHUFB` rotate-and-splat plus
  `AESENCLAST` with the `Rcon` vector as its round key: OpenSSL's `aesni-x86_64.pl` has this as `.L10rounds_alt`,
  selected on "AVX, but no XOP". The other is `AESKEYGENASSIST` plus a `PSHUFD` splat, as Go and Intel's white paper
  do. `PSHUFB` needs SSSE3, so the x86 backend would check `aes` and `ssse3`, as Go does. `AESKEYGENASSIST` takes its
  `Rcon` as an immediate, so its rounds must be unrolled, by a macro. Try both on CI, and test correctness here under
  Rosetta and Docker.
- Gate: AES-128 and AES-256 key setup at least 1.5x faster than K1 on the M1; on CI x86, at least not slower than K1.
- Tests: none to add; `matches_scalar_backend` already compares every round key.
- Docs: the `sub_word` descriptions in the `aarch64.rs` and `x86.rs` headers.

### P1. A multi-block API (decision Q1)

```rust
/// Encrypts every block of `blocks` in place: the same as `encrypt_block` on each in turn.
fn encrypt_blocks(&self, blocks: &mut [Self::Block]) {
    for block in blocks {
        *block = self.encrypt_block(block);
    }
}
// and `decrypt_blocks`, the same with `decrypt_block`
```

Both are default methods, so the trait stays implementable as it is. This is the pattern of `Digest::digest_many`,
which MD5 and SHA-3 override. AES overrides both, and its dispatcher checks the CPU once per call instead of once per
block. The methods work in place on `[[u8; 16]]`; a caller holding `&mut [u8]` uses `as_chunks_mut::<16>()`. This is
the building block that the planned modes need: CTR keystream, GCM, CBC and ECB decryption, XTS. It plays the role
that `ctrBlocks8` plays in Go. The docs must repeat the ECB warning.

Limit: modes in which each block waits for the previous one, such as CBC encryption and CMAC, cannot use any of
this. Their floor is the dependent chain: 10 × 3 = 30 cycles per AES-128 block on the M1 (about 1.6 GiB/s), and 40 on
a core where `AESENC` takes 4 cycles.

- Tests:
  1. `matches_scalar_backend` also runs each backend's multi-block function on every length from 0 to 2W+1 (every
     tail shape), against scalar one block at a time.
  2. `unaligned_input` also covers the multi-block path, with blocks at every offset.
  3. `known_answers` passes the four-block SP 800-38A ECB vectors once through `encrypt_blocks` and
     `decrypt_blocks`.
  4. `block_cipher::tests` checks the default methods.

  The prototypes passed such a comparison at lengths 0–100, natively and under Docker amd64. Keep the names of tests
  that the README and CONTRIBUTING cite.
- Docs: `block_cipher.rs`, the "Using it" section of `aes/mod.rs`, the README AES Usage example, and the dispatch
  comment in `cipher.rs` ("once per block as well as once per key").

### A1. aarch64: 8 blocks per round

The prototype loads all `N` round keys into registers once per call, then runs groups of W blocks. Each round does
`AESE` + `AESMC` on every block of the group, and the last round does `AESE` + `EOR`. The tail runs one block at a
time.

```rust
fn encrypt_group<const N: usize, const W: usize>(k: &[uint8x16_t; N], group: &mut [[u8; 16]; W]) {
    let mut s: [uint8x16_t; W] = [vdupq_n_u8(0); W];
    for j in 0..W { s[j] = load(&group[j]); }
    for key in &k[..N - 2] {
        for j in 0..W { s[j] = vaesmcq_u8(vaeseq_u8(s[j], *key)); }
    }
    for j in 0..W { group[j] = store(veorq_u8(vaeseq_u8(s[j], k[N - 2]), k[N - 1])); }
}
```

In the asm, LLVM keeps every pair adjacent on one register, so all of them fuse: 81 of 81 `AESMC`s for W=8 and AES-128.
It spills nothing for W ≤ 12. At W = 16, the blocks plus 15 keys exceed the 32 registers: LLVM rolls the round loop
and spills keys.

The table is from B1's other-crate harness, natively, in MiB/s, as the median of 3:

| Workload | W=1 | W=2 | W=4 | W=8 | W=12 | W=16 |
|----------|-----|-----|-----|-----|------|------|
| AES-128 encrypt | 11797 | 12968 | 13179 | **14618** | 15550 | 16100 |
| AES-128 decrypt | 11844 | 13316 | 12886 | **14678** | 15793 | 16114 |
| AES-192 encrypt | 9730 | 11024 | 10571 | **12174** | 12960 | 12131 |
| AES-256 encrypt | 8205 | 9484 | 8837 | **10164** | 10232 | 11072 |
| AES-128 encrypt, runtime dispatch | 11844 | 13154 | 13122 | **14757** | 15683 | 15734 |

Against D1's best per-block loop, W=8 is +25% (AES-128), +26% (AES-192) and +24% (AES-256). Against the
runtime-dispatched per-block loop it is 2.1x. Runtime dispatch costs nothing here, because the check runs once per
call. A 256 KiB in-cache run agrees with the 64 MiB run to within 1–5% at W ≥ 8, so the loop is compute-bound, not
memory-bound. W=8 is 3.3 cycles per block for AES-128, against the 2.5 floor.

Take W = 8: it is Go's width, it leaves free registers next to 15 keys, and it saturates any core whose latency ×
throughput product is at most 8. For the tail, try Go's 4/2/1 against singles.

- **A1b**: W = 12 is 4–9% faster on the M1 (AES-128 15550 against 14618, AES-192 12960 against 12174; AES-256 about
  equal). The M1 needs 12 fused pairs in flight. Take it only if the CI Arm runner (a Neoverse core) is not slower at 12
  than at 8.
- Gate: on the M1, `encrypt_blocks` at least 1.2x D1's per-block figure for every key size. On the CI Arm runner,
  where dispatch is at runtime, at least 1.5x the per-block figure.
- Docs: the `aarch64.rs` header; the README backend table and benchmark prose.

### X1. AES-NI, 8 blocks per round

16 XMM registers cannot hold 8 blocks and 15 keys, so each round key is loaded once per group (`movdqu` + 8 `aesenc`),
as in Go's `ctrBlocks8Asm`. The prototype is written in intrinsics like the aarch64 one, and LLVM compiles it to
nearly that. Its AES-128 loop is 120 instructions for 8 blocks: 80 `aesenc`/`aesenclast`, 8 block loads and 8 stores,
and 11 `movdqa` reloads of round keys that LLVM hoisted into aligned stack slots (the rest stay in registers). LLVM
rolled the AES-256 loop to 4 rounds per iteration (its unroll threshold), which is harmless here.

llvm-mca gives 10.0 cycles per block on skylake (the bound at 1 `AESENC` per cycle) and 5.0 on alderlake and znver3/4.
Today's per-block call from another crate is 30–37. OpenSSL uses the same width, and its `aesni-x86_64.pl` header
gives ECB on Haswell as 0.63 cycles/byte, which is 10 cycles per block. Decryption is the same with `aesdec`.

- Correctness: the full suite under Docker amd64 and under Rosetta.
- Gate (CI): at least 2x the per-block figure of the same job. Report it against Go's CTR in the same job too.
- Docs: the `x86.rs` header; the README's x86 figures, once they exist.

### X2. VAES-256: two blocks per instruction, 16 per group (decision Q3)

The VAES intrinsics (`_mm256_aesenc_epi128`, `_mm256_aesenclast_epi128`, `_mm256_aesdec_epi128`,
`_mm256_aesdeclast_epi128`) have been stable since Rust 1.89, so they are within the MSRV of 1.95. The backend is
compiled with `#[target_feature(enable = "vaes,avx2")]`. Dispatch goes `vaes && avx2` → X2, else `aes` → X1, else
scalar. Eight YMM registers hold the state of 16 blocks, and each round key is copied into both halves of a YMM
register with `vbroadcasti128`.

The prototype's AES-128 loop is 105 instructions per 16 blocks, 80 of them `vaesenc`/`vaesenclast`. LLVM hoisted
all 11 broadcast keys into YMM registers. With only 16 registers, that left room for 5 of the 8 states, so 3 states
spill (6 stack moves per group). llvm-mca still gives 2.5 cycles per block on alderlake and znver3/4, twice X1.
The implementation should still not rely on the hoisting. Instead, it should keep the broadcast keys in a 32-byte-aligned
stack array, filled once per call, so that each round takes its key as a memory operand and all 8 states stay in
registers. This applies to AMD Zen 3 and later and to Intel Ice
Lake and later, including Alder Lake. Cores without VAES (the Skylake family) stay on X1.

- Correctness is the hard part, since nothing here can execute VAES. There are two options:
  - (a) CI only. `matches_scalar_backend` covers X2 when the `ubuntu-latest` runner has `vaes`, and `--nocapture`
    makes the check-test log name it. If the runner lacks it, the test silently skips.
  - (b) Also a model. Make X2's group function generic over its 256-bit round operation. A test then instantiates it
    with two `AESENC`s on the 128-bit halves, which runs under Docker's AVX2. This is how SHA-NI was checked.

  The recommendation is (a) and (b).
- Gate: at least 1.3x X1 on a runner with VAES; otherwise drop it.
- AVX-512 (`zmm`, four blocks per instruction) is deferred until X2's figures exist and a runner reports `avx512f`
  together with `vaes`.

## 5. Scalar

### S1. Two blocks at a time, in the multi-block path

One scalar block is latency-bound: 445 MiB/s is about 108 cycles per block, or 10.8 per round, along the chain of byte
extract, table load, three XORs and key XOR. Interleaving two independent blocks round by round raises AES-128 from
419 to **637 MiB/s (+52%)** on the M1. The prototype `encrypt2` is `encrypt` with the round body written out twice.
In the probe harness the single block reads 419, against 445 in `throughput`. When implementing, also try 3 and 4
blocks; the load units are the next limit.

- This only applies to `encrypt_blocks` and `decrypt_blocks` (P1); single blocks stay as they are. It matters where
  the scalar backend is what runs: x86 without AES-NI, Arm cores without the crypto extension (the Raspberry Pi 4's
  Cortex-A72 is the common one), and riscv64. It is still table-based and leaks exactly as before (decision Q5).
- On x86, with its 16 GPRs, two blocks' state plus temporaries may spill. Check the scalar row of the CI x86 job.
- Gate: at least 1.3x on the M1, and no regression in the scalar rows of the x86 and Arm CI jobs.

## 6. Order of work, and how each step is verified

1. **B1**, so that every later step is measured on both sides.
2. **D1** and **K1**: small, local, and independent of each other.
3. **P1** with **A1** (and the A1b experiment), then **S1** and **K2** for aarch64.
4. **X0 → X1 → K2 for x86 → X2**, on CI.

Every step:

- `make ci`.
- Strict rustdoc: `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps`, also with `--document-private-items` and, for x86
  work, `--target x86_64-unknown-linux-gnu`.
- Clippy on the host, `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`.
- x86 code: the full suite under
  `docker run --platform linux/amd64 -v $PWD:/src:ro -e CARGO_TARGET_DIR=/tmp/t -w /src rust:1-slim cargo test`,
  and under `--target x86_64-apple-darwin`.
- New backends: a throwaway mutation pass (wrong key index inside the group, an off-by-one in the tail, a group read
  from an address rounded down to 16). The README must not claim it, since the harness is not in the repo.
- Timing: check `uptime` first. Use `--test-threads=1`, alternate the A and B builds in separate `CARGO_TARGET_DIR`s,
  and take the best of 5 within a run and the median of 3 runs. Anything about inlining is also checked from B1's
  separate crate.
- Keep the `*.rs` docs free of Go and of this machine's numbers; those belong in the README and `bench/`.

## 7. Considered and rejected

- **K3: a cheaper wipe.** `write_volatile::<[u8; 16]>` is lowered through a stack temporary, which the asm shows as
  `stp xzr, xzr, [sp]` → `ldr q0, [sp]` → `str q0, [key]`, 22 times per AES-128 drop. Writing `[u8; 8]` gives the same
  pattern with twice the stores, and was slower (90 against 78 ns). Integer stores need an aligned schedule;
  `#[repr(C, align(16))]` plus `u64` stores measured 78 → 79 ns (AES-128) and 100 → 108 (AES-256). The wipe is off the
  critical path, so it stays as it is.
- **D2: an out-of-line `#[cold]` scalar fallback.** Under runtime dispatch, 7247 → 7218 MiB/s, no change. On x86, D1
  already moves the frame out of the loop.
- **16 blocks on aarch64.** It exceeds the register file (spills and a rolled loop), and is slower than 12 for AES-192.
- **Aligning the schedule for x86 load folding.** Legacy-SSE `aesenc xmm, m128` requires 16-byte alignment, which is
  why LLVM emits separate `movdqu`s. In X1 that is one load per round per 8 blocks, and the VEX encodings in X2 fold
  unaligned operands anyway.
- **Encryption-only schedules** for CTR or GCM users: they would save 9–13 `AESIMC`s and half the memory, but after K2
  that part costs a few ns. Go builds both directions too (its arm64 key schedule has a `dec == nil` exit, but nothing
  in 1.27.1 calls it). Revisit this with the modes.
- **Explicit fusion hints** (`asm!`) on aarch64: LLVM already emits fusible pairs everywhere.
- **A constant-time (bitsliced) scalar**: a security change, not a speed one, and slower per block. See Q5.

## 8. Decisions needed

- **Q1.** Should P1 add `encrypt_blocks`/`decrypt_blocks` to `BlockCipher` as default methods, or should they be
  inherent methods on the AES types only? Recommended: the trait. Default methods break no implementor, and the modes
  will be generic over `BlockCipher`. It is a 0.x minor version bump.
- **Q2.** X0 and every x86 gate need a pushed branch and a dispatch of the Benchmarks workflow. OK to do that when we
  get there?
- **Q3.** Should X2's correctness rest on CI alone, or on CI plus a software model of the 256-bit instructions?
  Recommended: both.
- **Q4.** Should B1's other-crate benchmark be a crate under `bench/aesdownstream/` (a new Makefile target and a
  `bench.yml` step), or a `[profile.downstream]` in `Cargo.toml` plus `tests/`? Recommended: the `bench/` crate, which
  leaves the package's own manifest alone.
- **Q5.** The scalar stays table-based, and so not constant-time, which matters most on Arm cores without the crypto
  extension and on x86 without AES-NI. Is a constant-time fallback a separate plan, or out of scope?

## Appendix: reproducing the measurements

- **Another crate.** Copy `Cargo.toml` and `src/` to a scratch directory, then build a separate binary crate with
  `cryptors = { path = ... }` and the default release profile. It runs the 64 MiB per-block loop
  (`*b = cipher.encrypt_block(b)`) with a warm-up and the best of 5. The variants are `lto = "fat"`, `#[inline]` on
  the three methods of the `aes!` macro, and `RUSTFLAGS="-C target-feature=-aes"`. Check that the variants' binaries
  differ (`cmp`) before timing them.
- **Multi-block prototypes.** Add `encrypt_blocks::<N, W>` to the backend and a generic inherent
  `encrypt_blocks_w::<W>` to the AES types. Probe functions marked `#[unsafe(no_mangle)]` in `lib.rs` give monomorphic
  copies for the asm. For the in-cache variant, a `SMALL` environment variable switches to a 256 KiB buffer repeated
  256 times.
- **llvm-mca.** `cargo rustc --release --lib --target x86_64-unknown-linux-gnu -- --emit asm`, then extract the
  instructions between the hot loop's label and its backward branch, and run
  `/opt/homebrew/opt/llvm/bin/llvm-mca -mtriple=x86_64-unknown-linux-gnu -mcpu=<cpu> -iterations=300` on them. The
  figure is Total Cycles / 300 / blocks per iteration. The per-block rows are the caller's loop, the `encrypt_block`
  fast path and `x86::encrypt`, concatenated.
- **Latencies.** An `asm!` loop of 2×10^7 iterations, best of 7, divided by the cycle time that an 8-deep
  `add x, x, y` chain measured in the same run. Examples: `aese v0.16b, v8.16b; aesmc v0.16b, v0.16b` repeated (3.0);
  the same with `aesmc v1.16b, v0.16b` alternating registers (5.0); one pair on each of 12 registers v0–v7 and
  v10–v13 (0.27); `dup v16.4s, w9; aese v16.16b, v17.16b; umov w9, v16.s[0]` (15.1).
- **Key setup.** 2^20 keys per size with byte `j` = `31·i + j`, `C::new(black_box(k))` followed by
  `black_box(&c)` and the drop, best of 7. Go: the same keys through `aes.NewCipher`.
